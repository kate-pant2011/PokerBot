# Целевая архитектура и миграция

**Статус:** Proposed

## Подход

Так как `@TiltClub_bot` уже используется, новая модель внедряется внутри существующего приложения постепенно. Полная перепись с одновременным переключением создаёт лишний риск для данных, webhook и привычных сценариев.

```text
Telegram handlers ----\
                       -> application use cases -> domain rules
FastAPI routers -------/              |
                                      v
                              repositories / unit of work
                                      |
                               PostgreSQL + outbox
```

## Ответственность слоёв

- **Interfaces**: Telegram handlers и FastAPI routers разбирают ввод, вызывают один use case и отображают результат. Здесь нет формул и прямого изменения ORM.
- **Application**: `mark_arrived`, `start_tournament`, `seat_late_arrival`, `record_elimination`, `plan_rebalance`, `finish_tournament` задают транзакционные границы, авторизацию и идемпотентность.
- **Domain**: чистые правила состояний, рассадки, порядка мест и очков.
- **Infrastructure**: SQLAlchemy repositories, Alembic, Telegram gateway, clock, random source и durable scheduler/outbox.

Clock и random source передаются как зависимости, чтобы таймеры и случайный выбор можно было детерминированно тестировать.

## Надёжность

- Telegram update/callback идентифицируется и не обрабатывается повторно.
- Изменение домена и запись исходящего уведомления происходят в одной транзакции; отправка выполняется после commit с повторами.
- Webhook проверяет secret token, не логирует полный payload и возвращает ошибку, если update не принят в обработку.
- Регистрация webhook не удаляет очередь обновлений без отдельного операционного решения; shutdown процесса не должен снимать production webhook.

## Совместимость данных

Используется expand–migrate–contract:

1. добавить новые таблицы/поля без удаления legacy;
2. писать новые факты параллельно или включить новый путь feature flag-ом;
3. backfill только тех данных, семантика которых однозначна;
4. сравнить результаты и переключить чтение;
5. выдержать период наблюдения и только потом удалить legacy.

`eliminated_by_id`, `Player.elo` и `EloHistory` сохраняются на этапе совместимости, но не становятся частью нового домена. Для неизвестных исторических данных нельзя изобретать сезон или формулу задним числом.

## Границы первой версии

Первая версия может продолжать использовать FastAPI, aiogram, SQLAlchemy и PostgreSQL. Новые сервисы и брокер сообщений не обязательны: outbox и durable таймеры можно реализовать таблицами БД и фоновым worker в том же deployable, сохранив возможность вынести worker позднее.
