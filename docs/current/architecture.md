# Текущая архитектура

**Статус:** Current **Проверено на commit:** `ed5ce0617dc8ebfee4f7a396153a4a813647cf79`

## Контур приложения

Один Python-процесс запускает FastAPI и aiogram:

```text
Telegram -> POST /webhook -> aiogram Dispatcher -> handler
                                        |
REST client -> FastAPI router ----------+-> service -> database -> PostgreSQL
```

- `app/main.py` создаёт FastAPI, `Bot` и `Dispatcher`, регистрирует webhook и подключает Telegram routers и REST routers.
- `app/bot/handlers/` содержит команды, callbacks, poll answers и часть оркестрации сценариев.
- `app/services/` содержит проверки и часть бизнес-логики.
- `app/database/` выполняет SQLAlchemy-запросы.
- `app/models/` и `app/schemas/` задают ORM- и API-модели.
- `alembic/` содержит миграции PostgreSQL.
- `nginx/default.conf` проксирует весь HTTP-трафик на `backend:8000`.

Границы слоёв неполные: handlers напрямую обращаются к database-функциям и изменяют ORM-объекты. Одинаковое действие через Telegram и REST поэтому может вести себя по-разному.

## Существенное текущее поведение

- При старте игры `distribute_tables()` создаёт в БД один `Table(number=1)` и прикрепляет к нему всех участников.
- Несколько столов существуют только в ответе `fictitious_table_players()` и в сообщениях пользователям. Это представление, а не сохранённая рассадка.
- `/shuffle` заново формирует такое представление, но не сохраняет фактические перемещения между несколькими объектами `Table`.
- Выбывание деактивирует `TablePlayer`, присваивает место по числу активных игроков и сохраняет `eliminated_by_id`.
- Закрытие стола записывает `EloHistory` и меняет `Player.elo`. Несмотря на имя, активная формула — позиционное начисление, а не парное Elo-сравнение.

## Технические ограничения перед развитием

- Репозиторий нельзя воспроизводимо запустить из чистого clone: отслеживаемого `app/config/` и `docker-compose.yml` нет.
- Схема транзакций зависит от отсутствующей реализации `get_db`; закомментированный middleware не используется.
- Нет автоматических тестов и CI.
- В webhook не проверяется Telegram secret token; исключения подавляются и возвращается `{"ok": true}`.
- При запуске webhook регистрируется с `drop_pending_updates=True`, при штатном завершении удаляется. Для production это риск потери обновлений и простоя.
- В stdout выводится полный Telegram update; REST-доступ проверяет переданный клиентом `tg_id`, но отдельной аутентификации в отслеживаемом коде нет.

Это не список утверждённых задач, а ограничения, которые необходимо учитывать при миграции работающего бота.
